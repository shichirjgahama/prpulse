# Индексация и граф

## 1. Режимы импорта

| Режим | Когда использовать | Что делает |
| --- | --- | --- |
| `full` | первый импорт или смена проекта | очищает данные репозитория, читает всю историю, все файлы HEAD и создаёт срезы HEAD, тегов и веток |
| `incremental` | обычное обновление | дочитывает коммиты после старого HEAD, разбирает только изменённые файлы, пересобирает анализ из БД, обновляет срез HEAD |
| `rebuild` | повреждение данных, смена схемы анализа | удаляет состояние проекта и выполняет полный импорт заново |

Команды:

```powershell
python -m projectpulse index --repo samples\pluggy --mode full
python -m projectpulse index --repo samples\pluggy --mode incremental
python -m projectpulse index --repo samples\pluggy --mode rebuild
```

В GUI те же режимы доступны кнопками "Полный", "Инкремент", "Пересборка" на экране "Проекты".

## 2. Полный импорт по шагам

1. Проверка, что путь является Git-репозиторием; чтение HEAD и ветки.
2. Очистка прежних данных репозитория, создание записи `runs` со статусом `running`.
3. `git log --numstat` с шаблоном багфикса: коммиты, авторы, вставки, удаления, изменения файлов.
4. Чтение дерева HEAD и пакетное чтение blob-объектов.
5. Разбор Python-файлов через `ast`: LOC, SLOC, комментарии, пустые строки, функции, классы, сложность, импорты, ссылки, TODO.
6. Запись файлов, сущностей, ссылок и импортов.
7. Построение двух графов: файлового и сущностного.
8. Чтение истории публичного API для 24 самых изменяемых файлов.
9. Создание срезов графа: HEAD, до 8 тегов, до 5 веток. Для срезов используется общий кэш разбора.
10. Расчёт метрик, правил и индекса здоровья.
11. Запись результатов и завершение запуска.

Если файл не разбирается, он сохраняется с `parse_error`, а импорт продолжается. Файлы больше 1.5 МБ пропускаются. Число файлов в срезе ограничено 2500.

## 3. Инкрементальный импорт

Инкрементальный режим проверяет, что старый HEAD является предком нового. Если история разошлась или старый HEAD неизвестен, выполняется полный импорт с предупреждением. Это защищает от противоречивого состояния.

Далее:

1. `git log old_head..HEAD` даёт только новые коммиты.
2. Множество изменённых путей определяет, какие файлы перечитывать.
3. Для изменённых файлов, которые есть в новом дереве, выполняется разбор и замена строк файла, сущностей, ссылок и импортов.
4. Для изменённых файлов, которых больше нет, данные удаляются.
5. Неизменённые файлы не читаются из Git повторно.
6. Графы файлов и сущностей пересобираются из актуального состояния БД.
7. История публичного API пересчитывается для 24 самых изменяемых файлов по накопленным коммитам.
8. Срез HEAD обновляется, если коммит HEAD изменился. Срезы тегов и веток не пересоздаются.
9. Метрики, правила и здоровье пересчитываются полностью.

Важно: инкрементальный режим ускоряет чтение и разбор, но не является инкрементальным расчётом каждой метрики. Анализ всегда строится из согласованного состояния БД. Такой компромисс выбран ради корректности: многие метрики зависят от всей истории, а не от последнего коммита.

## 4. Кэш разбора

При полном импорте одни и те же файлы встречаются в HEAD и в срезах тегов или веток. Кэш `dict[(ref, blob_sha), ParsedFile]` исключает повторный `ast.parse` для одинакового содержимого.

Эффект: число вызовов `analyze_bytes` снизилось с 2181 до 718 на демонстрационном наборе, а тёплый проход по 179 файлам занял 1.155 мс против 367 мс холодного разбора. Подробнее: [performance.md](performance.md).

## 5. Две проекции графа

### Проекция файлов

Узел - Python-файл. Ребро `import` связывает файл-источник с файлом-целью. Разрешение импортов учитывает:

- абсолютные импорты `package.module`;
- относительные импорты `from .x import y` с уровнем;
- `src`-layout (`src/package/module.py`);
- `__init__.py` как пакет;
- неоднозначные имена: выбирается более короткий путь, затем лексикографически меньший.

Проекция отвечает на вопросы: какие файлы связаны, где циклы, какие модули являются посредниками.

### Проекция сущностей

Узлы - модули, классы, функции и методы. Рёбра:

- `call` - вызов функции или метода;
- `inherit` - наследование класса;
- `use` - использование имени;
- `compose` - композиция через атрибут или аннотацию.

Разрешение ссылки ищет совпадение по имени, затем по квалифицированному имени, затем по тому же файлу и родительскому классу. При неоднозначности выбирается детерминированный кандидат.

Проекция отвечает на вопросы: кто вызывает функцию, кто наследует класс, какие сущности образуют связную группу.

## 6. Алгоритмы графа

Все алгоритмы реализованы вручную в `analysis/graph.py`:

- итеративный Тарьян для компонент сильной связности;
- выделение циклов, включая петли;
- топологическая сортировка с учётом уникальных предшественников;
- fan-in, fan-out и степени;
- diff двух графов: добавленные, удалённые и изменённые узлы и рёбра.

Итеративный Тарьян не использует рекурсию, поэтому безопасен на больших графах. Топологическая сортировка не путает параллельные рёбра разных типов с циклом.

## 7. Версионирование срезов

Срез - неизменяемый снимок графа в таблицах `graph_snapshots`, `snapshot_nodes`, `snapshot_edges`.

- Полный импорт создаёт срез HEAD, срезы последних тегов и веток.
- Инкрементальный импорт создаёт срез HEAD, только если HEAD изменился и среза для этого коммита ещё нет.
- Срез содержит commit SHA, метку, число узлов и рёбер, число циклов, суммарный LOC и JSON с метриками.
- Сравнение срезов показывает добавленные и удалённые узлы и рёбра, а также изменения сложности и LOC.
- В GUI срез выбирается в выпадающем списке на экране "Граф"; отображаются узлы, рёбра, циклы и diff к предыдущему срезу.

## 8. Ограничения и устойчивость

| Параметр | Значение | Смысл |
| --- | ---: | --- |
| `max_file_bytes` | 1 500 000 | файлы больше лимита пропускаются |
| `max_snapshot_files` | 2500 | предел файлов в одном срезе |
| `max_snapshot_tags` | 8 | число тегов для срезов |
| `max_snapshot_branches` | 5 | число веток для срезов |
| `ivi_files_limit` | 24 | файлов для истории публичного API |
| `ivi_commits_limit` | 20 | коммитов на файл для IVI |
| `git_timeout` | 120 с | таймаут одной git-команды |
| `history_timeout` | 180 с | таймаут чтения истории |

Дополнительно:

- ошибка Git в одном срезе не отменяет остальные срезы;
- отмена проверяется между файлами, срезами и фазами;
- журнал фаз пишется в `stats_json`;
- повторный импорт без изменений всё равно обновляет метрики и здоровье, но не разбирает файлы.

## 9. Воспроизводимость импорта

- Репозитории фиксируются на коммитах из `repos.json`.
- Метрики времени считаются от максимального timestamp коммита, а не от даты запуска.
- Списки файлов, узлов, рёбер и находок сортируются.
- Срезы создаются в стабильном порядке: HEAD, теги, ветки.
- Прогресс и журнал не влияют на результаты анализа.
