# Правила риска и индекс здоровья

## 1. Как устроены правила

Правило - класс с атрибутами `name`, `version`, `description`, `trend` и методом `evaluate(ctx, metrics)`. Оно возвращает список `Finding`:

```text
rule            идентификатор правила
severity        critical | warning | info
target          файл, модуль, сущность или проект
title           короткое название
explanation     почему сработало, с числами и порогами
recommendation  что сделать
value           JSON со значениями для отчёта
```

Движок `evaluate_rules` изолирует исключения: падение одного правила не отменяет остальные. Находки сортируются по важности, цели и названию. Все пороги находятся в `Thresholds` и могут быть переопределены `thresholds.json`.

## 2. Каталог правил

| N | Правило | Тренд | Уровень | Условие |
| ---: | --- | --- | --- | --- |
| 1 | `hotspot_complex_churn` | нет | warning / critical | сложность и churn выше порогов |
| 2 | `bus_factor_one` | нет | warning / critical | bus factor модуля равен 1 |
| 3 | `ownership_concentration` | нет | warning | доля одного автора в файле >= 0.85 |
| 4 | `dependency_cycle` | нет | critical / warning | цикл в графе файлов |
| 5 | `god_module` | нет | warning | высокие fan-in и fan-out при большом LOC |
| 6 | `churn_spike` | да | warning / critical | аномальный недельный churn |
| 7 | `churn_volatility_rise` | да | warning / critical | рост волатильности churn |
| 8 | `fix_pressure_trend` | да | warning / critical | рост доли багфиксов |

Четыре правила на трендах: `churn_spike`, `churn_volatility_rise`, `fix_pressure_trend`, `ownership_drift`.

## 3. Детали правил

### 3.1 Hotspot: сложный и часто изменяемый файл

```text
complexity >= max(8, P90 сложности)
churn_90d >= max(1, P75 churn)
critical, если complexity >= P95 и churn_90d >= P90
```

Поддержка, тесты, примеры и скрипты исключаются. Возвращается до 8 файлов, отсортированных по произведению нормированных сложности и churn.

**Почему.** Комбинация сложности и частых правок сильнее каждого фактора по отдельности: именно такие файлы чаще дают дефекты.

### 3.2 Bus factor равен 1

```text
bus_factor(module) <= 1
commits(module) >= 10
critical, если commits >= 20
```

**Почему.** Модуль с историей, но без второго носителя знаний, останавливается при уходе единственного автора.

### 3.3 Концентрация владения

```text
top_share(file) >= 0.85
commits(file) >= 5
```

**Почему.** Формально файл может иметь несколько авторов, но 85% изменений одного человека означают, что остальные не знакомы с кодом достаточно глубоко.

### 3.4 Цикл зависимостей

Правило берёт компоненты сильной связности размером больше одного узла и петли. Если в цикле участвует `__init__.py`, уровень понижается до `warning`: реэкспорт через пакет часто является осознанным приёмом, хотя и повышает связность. Остальные циклы - `critical`.

**Почему.** Циклы усложняют импорт, тестирование и повторное использование, а также затрудняют сборку.

### 3.5 Модуль-посредник

```text
fan_in >= 5
fan_out >= 5
LOC >= 300
```

**Почему.** Такой файл одновременно зависит от многих и нужен многим. Любое изменение в нём распространяется по проекту.

### 3.6 Скачок churn

```text
z-score недельного churn >= 2.5
только последние 12 недель
critical, если z >= 4.5
```

Z-score считается по всей недельной истории churn. Если стандартное отклонение равно нулю, аномалий нет.

**Почему.** Резкий всплеск изменений часто связан с крупным рефакторингом, миграцией или аварийным исправлением. Он требует проверки тестов и размера коммитов.

### 3.7 Рост волатильности churn

```text
recent = средний CV churn за последние 4 недели
previous = средний CV churn за предыдущие 4 недели
recent >= 0.45
если previous > 0: recent / previous >= 1.5
если previous = 0: recent >= 0.90
critical, если recent >= 0.90
```

**Почему.** Растёт не средний объём, а непредсказуемость потока изменений. Это ранний сигнал нестабильного процесса разработки.

### 3.8 Рост давления багфиксов

```text
recent = FPI за последние 45 дней
previous = FPI за период 45..180 дней
growth = (recent - previous) / max(previous, 1e-9)
если previous > 0: growth >= 0.5
если previous = 0: recent >= 0.25
recent >= 0.20
critical, если growth >= 2.0 и recent >= 0.5
```

**Почему.** Проект может выпускать много кода, но если растёт именно доля исправлений, качество падает. Правило указывает файл с наибольшим вкладом в давление.

### 3.9 Дрейф владения

```text
ownership_drift >= 0.35
authors >= 3
critical, если ownership_drift >= 0.70
```

**Почему.** Резкая смена ведущего автора между четырёхнедельными окнами означает передачу контекста. Если она не сопровождается ревью и документацией, возрастает риск ошибок.

### 3.10 Нестабильный публичный API

```text
interface_volatility >= 0.40
public_change_commits >= 3
```

**Почему.** Публичные `def` и `class` без подчёркивания образуют контракт. Частые изменения ломают потребителей и требуют версионирования.

## 4. Индекс здоровья

Индекс здоровья - число от 0 до 100. Оно получается вычитанием четырёх компонентов штрафа.

```text
score = clamp(100 - (penalty_risks + penalty_hotspots
                     + penalty_knowledge + penalty_structure), 0, 100)
```

### 4.1 Риски правил, максимум 45

```text
penalty_risks = 9.0 * critical + 4.5 * warning + 1.5 * info
```

Штраф ограничен 45. Одно критичное срабатывание стоит 9 баллов, предупреждение - 4.5, информация - 1.5.

### 4.2 Горячие точки, максимум 25

```text
complexity_factor = clamp(complexity_max / max(25, P90 сложности), 0, 1)
churn_factor = clamp(churn_90d / max(150, P90 churn), 0, 1)
file_risk = complexity_factor * churn_factor
penalty_hotspots = sum(топ-5 file_risk) * 6.0
```

Поддержка исключается. Штраф ограничен 25.

### 4.3 Концентрация знаний, максимум 20

```text
penalty_knowledge = 8.0 * avg_file_top_share
                  + 12.0 * (1 - min(bus_factor, 4) / 4)
```

Если истории изменений нет, штраф равен 0. Штраф ограничен 20.

### 4.4 Структура зависимостей, максимум 10

```text
penalty_structure = 2.5 * cycles
                  + 1.5 * api_volatile_files
                  + 2.5 * god_modules
```

Штраф ограничен 10.

### 4.5 Метки состояния

| Баллы | Метка |
| ---: | --- |
| 80-100 | Хорошее состояние |
| 60-79.9 | Умеренное состояние |
| 40-59.9 | Повышенный риск |
| 0-39.9 | Критическое состояние |

### 4.6 Примеры на демонстрационных данных

| Проект | Балл | Метка | Критично | Предупреждений | Информация |
| --- | ---: | --- | ---: | ---: | ---: |
| pluggy | 65.3 | Умеренное состояние | 0 | 4 | 0 |
| django-extensions | 41.6 | Повышенный риск | 1 | 9 | 2 |

Разница 23.7 балла объясняется прежде всего компонентом рисков: у проблемного проекта 12 срабатываний против 4, включая критичный цикл и нестабильный API.

## 5. Как читать объяснения

Каждая находка содержит не только текст, но и фактическое значение, порог и контекст. Пример:

```text
Максимальная сложность функции 24 (порог P90 = 17),
churn за 90 дней 480 строк (порог P75 = 120).
Высокая сложность вместе с частыми правками повышает вероятность дефектов.
```

Такой формат позволяет проверить срабатывание вручную и не воспринимать правило как чёрный ящик.

## 6. Настройка

Файл `thresholds.json` в домашнем каталоге приложения переопределяет поля `Thresholds`. Неизвестные ключи игнорируются, битый JSON возвращает значения по умолчанию. Пример:

```json
{
  "hotspot_complexity_percentile": 0.85,
  "churn_spike_z": 2.0,
  "ownership_share_high": 0.8
}
```

Пороги применяются при следующем импорте. Уже сохранённые находки не пересчитываются автоматически.
