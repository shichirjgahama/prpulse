# Метрики

## 1. Состав каталога

В проекте 10 встроенных метрик: 5 классических, 3 собственные и 2 временных ряда. Все они зарегистрированы в `default_metrics()` и доступны плагинам через `MetricRegistry`.

| N | Метрика | Тип | Основная единица | Где считается |
| ---: | --- | --- | --- | --- |
| 1 | `loc` | классическая | строки | файл, проект |
| 2 | `complexity` | классическая | баллы | сущность, файл, проект |
| 3 | `churn` | классическая | строки | файл, проект |
| 4 | `ownership` | классическая | доля | файл, модуль, проект |
| 5 | `bus_factor` | классическая | авторы | модуль, проект |
| 6 | `fix_pressure` | собственная | доля | файл, проект |
| 7 | `coupling_pressure` | собственная | связей на 1000 LOC | файл, модуль, проект |
| 8 | `interface_volatility` | собственная | доля | файл, проект |
| 9 | `churn_volatility` | временной ряд | коэффициент | проект |
| 10 | `ownership_drift` | временной ряд | доля | проект |

Поддерживающие ряды `churn_weekly`, `commits_weekly`, `bugfix_weekly` и `ownership_top_share` используются графиками, правилами и мини-исследованием. Они не входят в десятку самостоятельных метрик, а служат исходными данными.

## 2. Классические метрики

### 2.1 LOC

**Формула**

```text
LOC = число физических строк файла
SLOC = строки, содержащие код
comments = строки комментариев
blank = пустые строки
comment_density = comments / (SLOC + comments)
```

**Зачем нужна.** Размер - базовый контекст для сложности, churn и плотности изменений. Сам по себе LOC не является риском, но 5000 строк в одном файле и 50 строк в одном файле требуют разного управления.

**Область.** Файл и проект. Для проекта строки суммируются.

### 2.2 Цикломатическая сложность

**Формула**

```text
M = 1 + число решений в поддереве
```

Учитываются `if`, `for`, `while`, `except`, `if-expressions`, булевы операции (каждый дополнительный операнд), условия comprehension и ветки `match`. Вложенные функции, классы и лямбды не входят в сложность родителя: они считаются отдельно.

```text
complexity_total = сумма сложностей функций файла
complexity_max = максимум сложности функции
avg_function_complexity = complexity_total / functions
p90_function_complexity = 90-й процентиль сложности функций
complex_functions = число функций со сложностью >= 10
```

**Зачем нужна.** Сложные функции труднее тестировать и сопровождать. Максимум показывает худшую точку, среднее - общий уровень, P90 устойчив к выбросам.

**Область.** Сущность (только функции со сложностью от 8), файл, проект.

### 2.3 Churn

**Формула**

```text
churn_total = добавленные строки + удалённые строки за всю историю
churn_90d = churn за последние 90 дней относительно HEAD
churn_density_90d = churn_90d / max(LOC, 1) * 100
churn_per_commit = churn_total / commits
bugfix_share = число багфикс-коммитов / все коммиты
```

Багфикс определяется по регулярному выражению `bugfix_pattern` в сообщении коммита. Шаблон учитывает английские и русские слова: fix, bug, hotfix, issue, crash, regression, исправ, почин, баг.

**Зачем нужна.** Churn показывает стоимость изменений и турбулентность. Плотность на 100 LOC позволяет сравнивать файлы разного размера. Доля багфиксов - грубый индикатор качества и давления дефектов.

**Область.** Файл и проект.

### 2.4 Владение кодом

**Формула**

```text
changes(author) = сумма добавленных и удалённых строк автора
top_share = max(changes) / sum(changes)
H = -sum(p_i * log2(p_i)), p_i = changes_i / sum(changes)
H_norm = H / log2(authors), authors > 1
avg_file_top_share = среднее top_share по продуктовым файлам
single_owner_files = число файлов с одним автором
```

Владение считается по изменённым строкам, а не по числу коммитов: крупная правка одним автором весит больше мелкой.

**Зачем нужна.** Высокая доля одного автора и низкая энтропия означают концентрацию знаний. Это риск отпуска, увольнения и узкого места в ревью.

**Область.** Файл, модуль, проект. Тестовые и служебные пути исключаются из продуктовых агрегатов.

### 2.5 Bus factor

**Формула**

```text
BF = min k, при котором сумма k крупнейших вкладов >= 0.5 * сумма всех вкладов
```

Вклады - изменённые строки авторов. Если у проекта один автор, bus factor равен 1. Если вкладов нет, значение равно 0.

**Зачем нужна.** Bus factor прямо отвечает на вопрос: сколько человек должны уйти, чтобы проект потерял половину знаний. Низкое значение - критичный организационный риск.

**Область.** Модуль и проект. Для модулей дополнительно хранится число коммитов.

## 3. Собственные метрики

### 3.1 Fix Pressure Index, FPI

**Формула**

```text
w_t = 0.5 ^ (age_days / 60)
FPI = sum(w_t * is_bugfix_t) / sum(w_t)
FPI_growth = (FPI_recent - FPI_previous) / max(FPI_previous, 1e-9)
```

Окна: последние 45 дней и базовая история до 180 дней. Вес свежести имеет период полураспада 60 дней.

**Мотивация.** Обычная доля багфиксов смешивает старые и новые коммиты. FPI подчёркивает недавнее давление дефектов: если проект стал чаще исправлять ошибки, индекс растёт быстрее, чем при равномерном усреднении.

**Область.** Файл и проект. Для проекта веса суммируются по всем продуктовым файлам.

**Интерпретация.** 0.20 означает, что около 20% взвешенных изменений связаны с исправлениями. Порог правила - рост на 50% и не менее 20% в последнем окне.

### 3.2 Coupling Pressure, CP

**Формула**

```text
CP = (fan_in + 0.5 * fan_out) * (1 + 0.5 * in_cycle) * 1000 / max(LOC, 50)
```

Где `fan_in` - число входящих зависимостей, `fan_out` - исходящих, `in_cycle` равен 1, если файл входит в продуктовый цикл.

**Мотивация.** Абсолютные fan-in и fan-out несправедливы к большим файлам. Нормировка на LOC и штраф за цикл дают плотность связей: маленький файл с пятью входящими связями опаснее большого файла с теми же пятью.

**Область.** Файл, модуль, проект. Для проекта считаются среднее и максимум по файлам.

### 3.3 Interface Volatility Index, IVI

**Формула**

```text
w_t = 0.5 ^ (age_days / 180)
IVI = sum(w_t * public_api_changed_t) / sum(w_t)
```

Коммит считается изменившим публичный API, если в патче появилась или исчезла строка `def` или `class` с именем без ведущего подчёркивания. Анализируются 24 самых изменяемых файла, по 20 последних коммитов на файл.

**Мотивация.** Частые изменения публичных имён ломают потребителей. IVI измеряет не число коммитов, а долю свежих изменений, затрагивающих контракт модуля.

**Область.** Файл и проект. Для проекта IVI взвешивается по числу рассмотренных коммитов.

## 4. Временные ряды

### 4.1 Волатильность churn

**Формула**

```text
CV_t = stdev(churn[t-7..t]) / mean(churn[t-7..t])
churn_volatility = CV последней недели
churn_volatility_recent = mean(CV последних 4 недель)
churn_volatility_previous = mean(CV предыдущих 4 недель)
churn_spike_count = число недель с z-score churn выше 2.5
```

**Мотивация.** Средний churn может быть стабильным, но поток изменений - рваным. Высокий коэффициент вариации означает непредсказуемую нагрузку на ревью и тесты.

**Область.** Проект, недельные бакеты.

### 4.2 Дрейф владения

**Формула**

```text
share_t = top_share за окно из 4 недель, заканчивающееся неделей t
OD_t = |share_t - share_{t-4}|
ownership_drift = OD последней недели
ownership_drift_avg = среднее OD за последние 12 недель
ownership_drift_max = максимум OD
ownership_top_share_current = share последней недели
```

**Мотивация.** Даже при нормальном среднем bus factor резкая передача файлов или модулей создаёт разрыв контекста. Дрейф фиксирует именно скорость смены ведущего автора.

**Область.** Проект, недельные бакеты. Правило срабатывает при дрейфе от 0.35 и наличии минимум трёх авторов.

## 5. Где хранятся значения

- `metric_values` - значения запуска в разрезах `project`, `module`, `file`, `entity`.
- `series` - недельные ряды `churn_weekly`, `commits_weekly`, `bugfix_weekly`, `churn_volatility`, `ownership_drift`, `ownership_top_share`.
- `files` - быстрый доступ к LOC, сложности и TODO без распаковки JSON.
- `report.builder` собирает словарь `(scope, target, metric) -> value` для отчётов.

## 6. Проверка формул

Формулы покрыты тестами:

- `tests/test_metrics_rules.py` проверяет состав каталога, churn, владение, FPI, IVI, циклы и coupling.
- `tests/test_properties.py` проверяет границы корреляций, процентилей, bus factor и `safe_div`.
- `tests/test_pipeline.py` проверяет, что метрики появляются после полного и инкрементального импорта.
- `tests/test_report.py` проверяет наличие метрик в данных отчёта.

Пороги и параметры метрик находятся в `Thresholds` (`core/config.py`) и могут быть переопределены файлом `thresholds.json` в домашнем каталоге приложения.
