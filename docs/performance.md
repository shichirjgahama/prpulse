# Производительность

## 1. Что и как измерялось

Замеры выполнены на демонстрационном наборе из `repos.json` на локальном диске. Основной полигон - `django-extensions`: 2889 коммитов и 246 Python-файлов. Использовались три инструмента:

| Инструмент | Команда | Что показывает |
| --- | --- | --- |
| `cProfile` | `python scripts/profile_index.py` | распределение времени полного импорта по функциям |
| микробенчмарк | `python scripts/microbench.py` | эффект пакетного чтения blob и кэша разбора отдельно |
| `bench` | `python -m projectpulse bench --repo <путь>` | полный и инкрементальный проход на клоне с пробными коммитами |

Числа зависят от CPU, диска и версии Python. На момент подготовки отчёта использовался Python 3.14 на Windows; код совместим с Python 3.11+. Абсолютные секунды важны меньше, чем сравнение режимов и доказанный эффект оптимизаций.

## 2. Профиль полного импорта

Контрольный профиль находится в `reports/profile_full.txt`, бинарный профиль - в `reports/profile_full.prof`.

```text
15 378 245 вызовов функций за 9.971 с
index                    10.009 с
  _full                   9.650 с
    _parse_tree           5.831 с  (9 вызовов: HEAD, теги, ветки)
    _create_snapshots     5.713 с
    analyze_bytes         3.986 с  (718 вызовов)
    git _run              2.945 с  (39 вызовов)
    _interface_volatility 1.712 с
    read_blobs            1.305 с  (27 вызовов)
```

Что это значит:

- Разбор AST остаётся самой дорогой частью, но вызван 718 раз, а не 2181: сработал общий кэш срезов.
- `_create_snapshots` почти целиком состоит из `_parse_tree`, поэтому строка `5.713 с` пересекается с `5.831 с`, а не складывается с ней.
- Git-подпроцессы занимают около 3 секунд: история, деревья, патчи публичного API.
- История публичного API (`_interface_volatility`) - второй по стоимости источник после разбора.

## 3. Оптимизация 1: пакетное чтение blob-объектов

### Проблема

Исходная реализация читала содержимое файла отдельным процессом:

```text
git show HEAD:path/to/file.py
```

Для каждого файла создавался новый процесс Git. На 200 файлах это давало более 10 секунд почти целиком на запуск процессов, а не на полезную работу.

### Решение

`GitRunner.read_blobs` открывает один долгоживущий процесс:

```text
git cat-file --batch
```

SHA-объекты подаются в stdin, ответ читается из stdout: заголовок `sha type size`, затем ровно `size` байт и разделитель. Дубликаты SHA удаляются через `dict.fromkeys`, пустой список не запускает процесс. Разбор заголовка и короткое чтение защищены проверками: при неожиданном ответе возвращается `None`, а не исключение.

### Результат

Микробенчмарк в `reports/microbench.json`, 200 файлов `django-extensions`:

| Способ | Время |
| --- | ---: |
| последовательные `git show` | 10 303 мс |
| один `cat-file --batch` | 72 мс |
| ускорение | 143.1x |

Дополнительно в профиле видно, что 1.03 из 1.305 секунды `read_blobs` приходится на `readline`: это уже чтение самих данных, а не накладные расходы процессов.

## 4. Оптимизация 2: общий кэш разбора по паре путь и blob SHA

### Проблема

Полный импорт разбирает не только HEAD, но и срезы тегов и веток. Один и тот же файл встречается в нескольких срезах. Без кэша `ast.parse` и обход дерева выполнялись заново для каждого среза. В исходном профиле было 2181 вызов `analyze_bytes`.

### Решение

Кэш `dict[(path, blob_sha), ParsedFile]` живёт в течение одного импорта и передаётся во все вызовы `_parse_tree`:

- перед чтением blob проверяется пара `(path, sha)`;
- для пакета читаются только отсутствующие в кэше объекты;
- результат `analyze_bytes` сохраняется в кэш;
- ключ включает путь, потому что от пути зависят имена сущностей, импорты и квалифицированные имена.

Кэш не переживает импорт: данные не устаревают между запусками и не занимают память постоянно. Инкрементальный импорт разбирает только изменённые файлы, поэтому кэш ему почти не нужен, но он используется и там.

### Результат

| Показатель | До | После |
| --- | ---: | ---: |
| вызовы `analyze_bytes`, полный импорт | 2181 | 718 |
| время профиля полного импорта | 16.9 с | 11.1 с (контрольный прогон 9.971 с) |
| холодный разбор 179 файлов | 367 мс | 367 мс |
| тёплый проход по кэшу, 179 файлов | - | 1.155 мс |
| ускорение тёплого прохода | - | 317.8x |

Тёплый проход измеряет только попадание в кэш и не включает чтение blob. Поэтому 317.8x - верхняя граница эффекта кэша, а не обещание ускорения всего импорта. Реальное сокращение числа разборов - примерно в 3 раза, что и дало снижение полного профиля с 16.9 до 11.1 секунды.

## 5. Полный и инкрементальный импорт

Замеры `reports/benchmark.json`:

| Проект | Полный | Инкремент без изменений | Инкремент с одним коммитом |
| --- | ---: | ---: | ---: |
| pluggy | 3 696 мс | 1 711 мс | 2 315 мс |
| django-extensions | 7 558 мс | 2 094 мс | 3 180 мс |

Во всех инкрементальных проходах `commits_new` равен 0 или 1, а `files_parsed` - 0 или 1. Полный импорт разбирает 36 и 246 файлов соответственно.

Почему инкремент без изменений всё равно занимает 1.7-2.1 секунды:

1. Проверяется связь старого и нового HEAD через Git.
2. Метрики, правила и здоровье пересчитываются из состояния БД полностью.
3. История публичного API пересчитывается для 24 самых изменяемых файлов.
4. Создаётся запись запуска и обновляются агрегаты.

Это осознанный компромисс: инкрементальным сделано дорогое чтение и разбор, а расчёт метрик оставлен согласованным и полным. Иначе пришлось бы хранить промежуточные состояния каждой метрики и рисковать расхождением.

## 6. Как воспроизвести

```powershell
$env:PYTHONPATH = "src;."

python scripts\profile_index.py --repo samples\django-extensions --mode full
python scripts\microbench.py --repo samples\django-extensions --limit 200
python -m projectpulse bench --repo samples\django-extensions --runs 1 --json
```

Все три команды пишут результаты в `reports/`. Профиль инкрементального прохода:

```powershell
python scripts\profile_index.py --mode incremental --out reports\profile_inc.prof --text reports\profile_inc.txt
```

## 7. Что осталось дорогим

- `_interface_volatility` запускает `git log -p` по 24 файлам. Это следующий кандидат на кэш патчей по SHA коммита.
- SQLite-вставки выполняются в транзакциях, но по одной строке; пакетная вставка через `executemany` может дать ещё несколько процентов на больших историях.
- Парсер обходит AST несколько раз: сложность, сущности, ссылки. Один объединённый обход уменьшил бы постоянный множитель.
- Срезы тегов и веток создаются при каждом полном импорте. Для очень больших репозиториев их число ограничено 8 тегами и 5 ветками.

## 8. Вывод

Две оптимизации доказаны замерами, а не только рассуждением:

1. Пакетное чтение blob через `git cat-file --batch` ускорило чтение 200 файлов в 143 раза.
2. Общий кэш разбора сократил число вызовов `analyze_bytes` с 2181 до 718 и снизило время полного профиля с 16.9 до 11.1 секунды.

Инкрементальный режим на порядок дешевле полного по объёму разбора, но не по расчёту метрик. Это ограничение описано явно, чтобы не выдавать частичный инкремент за полный.
