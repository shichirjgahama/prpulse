# Мини-исследование

## 1. Гипотеза

> Рост churn и снижение доли ведущего автора на неделе t связаны с ростом числа багфикс-коммитов на неделе t+1.

Гипотеза проверяется на двух зафиксированных репозиториях: здоровом pluggy и проблемном django-extensions.

## 2. Данные

Для каждого проекта строятся недельные ряды по всей доступной истории Git:

- `churn_weekly` - добавленные плюс удалённые строки за неделю;
- `bugfix_weekly` - число коммитов с признаком багфикса;
- `ownership_top_share` - доля ведущего автора в окне из 4 недель;
- `churn_volatility` - коэффициент вариации churn в окне из 8 недель.

Багфикс определяется регулярным выражением по сообщению коммита. Владелец определяется по сумме добавленных и удалённых строк.

| Проект | Коммиты | Недель | Авторов | Средний churn/нед | Багфиксов/нед | Средняя доля лидера |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| pluggy | 850 | 603 | 78 | 72.9 | 0.19 | 62.8% |
| django-extensions | 2889 | 981 | 621 | 133.9 | 0.73 | 58.4% |

## 3. Методика

Для каждой недели t, кроме первой и последней, считаются:

```text
g_t = (churn_t - churn_{t-1}) / max(churn_{t-1}, 1)
d_t = max(0, share_{t-1} - share_t)
y_t = bugfix_{t+1}
```

- `g_t` - относительный рост churn;
- `d_t` - падение доли ведущего автора;
- `y_t` - число багфиксов на следующей неделе.

Составной предиктор:

```text
composite_t = z(g_t) + z(d_t)
```

Z-оценка использует выборочное стандартное отклонение (`n - 1`). Если отклонение равно нулю, все z-оценки равны нулю.

Проверяются четыре связи:

1. рост churn -> багфиксы;
2. падение доли лидера -> багфиксы;
3. составной предиктор -> багфиксы;
4. волатильность churn -> багфиксы.

## 4. Пирсон и Спирмен вручную

### 4.1 Пирсон

```text
r = sum((x_i - mean_x) * (y_i - mean_y))
    / sqrt(sum((x_i - mean_x)^2) * sum((y_i - mean_y)^2))
```

Если знаменатель близок к нулю, возвращается 0. Значение ограничивается диапазоном [-1, 1].

### 4.2 Спирмен

```text
rho = pearson(rank(x), rank(y))
```

При совпадениях используется средний ранг: группа одинаковых значений получает среднее арифметическое позиций. Это корректно обрабатывает недели с нулевым churn и одинаковым числом багфиксов.

### 4.3 Перестановочный p-value

```text
p = (1 + число перестановок с |rho_perm| >= |rho_obs|) / (B + 1)
B = 500
seed = 42
```

Перестановочный тест не требует нормальности и устойчив к выбросам. Seed фиксирован, поэтому результат воспроизводим. При менее чем трёх наблюдениях p-value равен 1.

### 4.4 Почему не scipy

Задание запрещает scipy. Все формулы реализованы в `analysis/stats.py` на стандартной библиотеке: `math` и `random`. Тесты `tests/test_stats.py` проверяют точные значения, средние ранги и детерминизм перестановок. `tests/test_properties.py` проверяет границы коэффициентов на случайных данных.

## 6. Интерпретация

- Связь "падение доли лидера -> багфиксы" статистически заметна в обоих проектах: rho = 0.122 и 0.126, p < 0.01. Это слабая, но устойчивая связь.
- Составной предиктор даёт rho = 0.104 в обоих проектах, p = 0.018 и 0.002. Направление совпадает с гипотезой.
- Рост churn сам по себе не показал значимой связи: p = 0.71 и 0.75. В недельной агрегации объём изменений слишком шумный.
- Волатильность churn значима только в проблемном проекте, но с отрицательным знаком. Это скорее артефакт длинных периодов без коммитов, чем подтверждение гипотезы.

**Вывод.** Гипотеза подтверждается частично: снижение доли ведущего автора связано с будущими багфиксами, но эффект слабый. Рост churn сам по себе не является надёжным предиктором. Причина может быть в том, что крупные изменения часто являются плановыми, а не аварийными.

## 7. Ограничения

1. Багфикс определяется по сообщению коммита, а не по содержанию изменений.
2. Недельная агрегация сглаживает короткие всплески.
3. Корреляция не доказывает причинность: возможны общие факторы (релизы, миграции, сезонность).
4. Владение считается по строкам, а не по экспертизе.
5. Перестановочный тест даёт грубую оценку при малом числе недель.
6. Репозитории имеют разную длину истории и разный стиль коммитов.

## 8. Воспроизводимость

```powershell
python -m projectpulse research `
  --healthy samples\pluggy `
  --problematic samples\django-extensions `
  --out reports\research_report
```

Команда создаёт `research_report.md` и `research_report.json`. Те же результаты формируются в GUI кнопкой "Исследование" на экране "Сравнение". Результат также сохраняется в таблицу `research_results`.
